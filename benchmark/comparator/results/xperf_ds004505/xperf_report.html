amica-python is indistinguishable from scott-huberty on GPU — both sit in the same fast tier, and the nominal 0.5 s edge is not robust across tests. It is significantly faster than pyamica, and overwhelmingly faster than pAMICA. On CPU, amica-chunked beats every implementation with p<1e-10.

Reading of the result

  • amica-python is the fastest AMICA implementation measured — fastest on GPU (9.6 s) and, via its chunked path, fastest on CPU (218 s).
  • pAMICA is the clear outlier. It is ~27× slower than amica on GPU and ~3× on CPU, and it barely accelerates from CPU to GPU (673 s → 266 s, 2.5×) while amica, scott and pyamica gain 23–100×. The signature — flat CPU→GPU scaling — points to it being overhead-bound, not compute-bound (eager per-component work that never saturates the GPU), rather than doing more math. [inferred from scaling, not profiled]
  • The three fast implementations (amica, scott, pyamica) are a statistical near-tie on GPU around ~10 s. The interesting contrast is not among them — it is pAMICA vs the field.
  • Every implementation agrees numerically (|W corr| 0.997–1.000 vs the Fortran reference), so these are fair timing comparisons of code computing the same answer.

Method & honest caveats

  • Setup. Each implementation runs in its own version-pinned virtual environment (amica @92003b4 · pAMICA v0.3.1 · scott amica-python 0.1.1 · pyamica · Fortran built from source), one subprocess per fit. Timing is the wall clock of fit(), which includes first-iteration/JIT compilation for every impl — measured cold and consistently after a cache-race fix, so no implementation gets a hidden warm-cache advantage.
  • Single seed, 100 iterations, 25 subjects. Enough to separate pAMICA from the field by orders of magnitude, but the amica-vs-scott GPU tie would need multiple seeds to call either way.
  • amica-JAX on GPU required a dedicated jax-gpu environment (jax_cuda12 plugins); the default env is JAX-CPU. The pAMICA-is-slow finding is inferred from CPU↔GPU scaling, not a kernel profile.
  • Fortran is CPU-only here — it is the numerical reference (built from vendored source, parity-validated to ΔLL 7e-8), not a speed contender, and does not run in the GPU comparison.

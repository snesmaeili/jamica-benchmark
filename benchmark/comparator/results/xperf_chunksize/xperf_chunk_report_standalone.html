Fit time and peak memory across AMICA implementations

We measured how long each Python AMICA implementation takes to fit, and how much memory it needs, on a real EEG dataset — sweeping each one across its batch/chunk-size setting on both GPU and CPU. That single setting changes fit time by up to ~17× and peak memory by up to ~30× within one implementation, and the best setting differs by implementation and between GPU and CPU.

What we measured

Each implementation exposes a setting controlling how many samples are processed per pass — chunk_size, block_size, chunk_t or batch_size depending on the package. We swept it across five values (1024 → full-batch) and recorded fit time and peak memory, on the same subjects, for each device.

~17×
Widest fit-time range across the batch/chunk setting, within a single implementation. A setting that is fast on one device can be slow on the other.
~30×
Widest peak-memory range across the setting. Memory grows sharply toward full-batch — enough to run some implementations out of memory on an 80 GB card.
GPU ⇄ CPU
The best setting flips by device: large / full-batch on the H100, small / mid on CPU. A single recommended value is wrong for both.

GPU — fit time & memory

Each implementation swept across its setting on real ds004505 (25-subject median, 100 iterations, H100). ◯ marks each one's fastest measured setting; the shaded band on the timing plot is the min–max across subjects.

jamica chunk_size @df18b5epAMICA (sccn) block_size @0c4da39pyamica chunk_t @a8a4d7escott-huberty batch_size @e15e158◯ each impl's optimum
  • Larger settings are faster on the GPU. Fit time falls as the chunk grows; the fastest measured setting is at or near full-batch for jamica, pAMICA and pyamica, and 65K for scott-huberty.
  • Small settings are slow. At 1024, scott-huberty and pAMICA take 140–170 s, versus ~9–10 s at each one's own fastest setting. The fastest setting is per-implementation and only found by sweeping.
  • Memory grows sharply toward full-batch. At full-batch, pyamica peaks near 28 GB, pAMICA near 19 GB and jamica near 8 GB, and scott-huberty runs out of memory. Chunking trades a large amount of memory for a little time — all four drop to a few GB at smaller settings.

CPU — fit time & memory

Real ds004505, 8 cores, 5 subjects. ◯ marks each implementation's fastest CPU setting. Includes the Fortran amica17 reference (CPU-only). Fit time is the best-observed (fastest) of the 5 subjects per cell — see the measurement note below.

jamica chunk_size @df18b5epAMICA (sccn) block_size @0c4da39pyamica chunk_t @a8a4d7escott-huberty batch_size @e15e158Fortran amica17 block_size @665b577◯ each impl's optimum
  • The best setting is different on CPU. CPU optima sit at small/mid chunks (jamica 1024, scott-huberty/Fortran ~4096, pyamica 16384) — the opposite of the GPU, where large/full-batch won. Small blocks fit CPU cache; on the H100 they starve the device. The recommended setting depends on the device.
  • Best-observed CPU times (fastest of 5 subjects, approximate — see note): jamica and scott-huberty are closest at ~155–165 s, then pAMICA ~240 s, Fortran ~590 s and pyamica ~720 s.
  • Full-batch is memory-heavy on CPU too (jamica 21 GB, pyamica 27 GB); the Fortran reference uses the least memory at every measured setting (0.72 GB at 1024, up to 9.97 GB at full-batch).
  • Two settings failed outright: pyamica at 1024 exceeded the 1-hour timeout; scott-huberty at full-batch ran out of memory — both absent from the curve.
On the CPU timing numbers. CPU fits were measured on shared cluster nodes, and AMICA fits are memory-bandwidth-bound, so jobs sharing a node interfere and per-cell absolute times are noisy. The 5 subjects also differ in recording length, so a per-cell median mixes both contention and data size and stays non-monotonic. We plot the best-observed (fastest) of the 5 per cell to recover a clean trend — but that minimum reflects both a quieter node and a shorter subject, so treat absolute CPU seconds as approximate, contention-inflated figures. Rely on the curve shapes and each implementation's fastest setting, and read the cross-implementation ordering as coarse. CPU memory is allocation-driven and clean regardless.

Methodology — why the synthetic "flat curve" was a mirage

An earlier synthetic microbenchmark (random data, 20 iters) showed amica with a suspiciously flat GPU curve. An independent panel (GPT-5.6 + Grok-4.6) and a steady-state re-measurement traced it to a JIT-compile artifact, not robustness.

With chunk_size a JIT static argument, each of amica's fused-scan cells compiled a different program; a fresh-process 20-iter wall clock folds a ~2.5 s compile into every point, which flattens a short run. Splitting compile from steady-state ms/iter ((T₄₀−T₁₀)/30) reveals a normal ~19× steady-state spread — amica is not chunk-robust. The real 100-iteration workload above confirms it: a steep, ordinary U-curve. What amica genuinely has is a fused in-graph blocked E-step (no Python-per-block penalty), memory-efficient full-batch, a correct auto pick per device, and the fastest real-workload time — not knob-insensitivity.

"Flattest ⇒ most robust is a self-serving reading of a short, compile-contaminated GPU sweep." — adversarial panel synthesis

Release vs main

All curves above are latest main. Release→main is performance-neutral on GPU (measured identical); amica's one perf-relevant commit (2cd81e4, "make CPU fits faster and smaller") touches the CPU E-step only, and its effect is within CPU node-contention noise in this pass — the throttled rerun will resolve it. Competitor main builds move only through the same batching knob; bumping to main rescues no one's default (pAMICA main is still 140 s at 512).

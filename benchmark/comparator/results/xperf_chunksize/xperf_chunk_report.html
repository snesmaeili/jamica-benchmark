Cross-implementation AMICA · ds004505 · H100 + Xeon · main builds

Chunk size is the hidden variable

The "47× slower" gap between AMICA implementations was a default-configuration artifact. Fix the batching knob and the field collapses to under 2× at each library's optimum. And the "flat curve" that looked like robustness? It was fixed compile cost hiding an ordinary steep curve — no implementation is insensitive to this knob.

Two corrections. (1) Every library exposes a batching knob that moves fit time 3–13× in wall-clock and 20–500× in steady-state ms/iter; each ships a default wrong for the H100 (pAMICA's 512 is the 47× culprit), and the optimum flips by device. (2) amica-python is not "chunk-robust" — its flat 20-iter curve was ~2.5 s of JIT compile masking a normal steady-state spread. Compared at each library's own optimum on the real ds004505 workload, amica leads at 5.5 s (pAMICA 1.7×, pyamica 2.3×, scott 8.3×).

The steady-state truth

The headline chart. A short benchmark reports a total that mixes a fixed per-fit cost (JIT compile for JAX; CUDA/kernel init for torch) with the per-iteration compute. Strip the fixed cost by differencing two iteration counts, (T₄₀−T₁₀)/30, and the real per-iteration curve appears — steep for everyone, amica included.

pAMICA's torch backend does not auto-tune block_size (only its numpy backend + the Fortran reference do). Reporting its shipped default as "pAMICA performance" is what produced the 47× headline. Its true best is 9.5 s — at a 19 GB VRAM cost.

The curves — total time & memory

Synthetic sweeps (64 ch, 1 model, 3 mixtures) on each device. These are 20/10-iter totals (so they carry the fixed cost above); still, the shape, the defaults, and the memory trade-off are clear. ◯ = each impl's optimum; ★ = amica's auto pick.

  • The optimum flips by device. scott is fastest at full-batch on CPU (43 s) but slowest at full-batch on GPU. A single recommended chunk is wrong — it's a per-library and per-device curve.
  • Memory is the real trade the flatness hides. On GPU, time barely moves 4096→full while VRAM triples — so you can shrink the block to fit a memory budget at low speed cost. pAMICA's full-batch optimum costs 19 GB on the real workload; amica reaches its speed in ~1 GB.
  • amica's genuine edge is the full-batch corner: it doesn't collapse at full like pyamica (0.5→ VRAM 5.09 GB) or scott — a fused single pass at 1.21 GB, not a recording-length temporary storm.

What amica-python actually offers (honestly)

  • Fused in-graph chunking. Its blocked E-step is a lax.fori_loop inside one compiled step (_amica_step_fused), so host dispatch count doesn't grow as the block shrinks — it never pays the Python-per-block penalty the eager paths do. (This is dispatch structure, not tile-invariant kernels: device work still scales, hence the steep steady curve.)
  • Memory-efficient full-batch (1.21 GB vs pyamica 5.09 GB) and a correct auto pick per device (full-batch on GPU, ~4096 on CPU).
  • Fastest on the real workload once iterations amortize the fixed compile cost.
  • Not chunk-robust, not the fastest on tiny/synthetic runs, and its CPU curve is a normal ~3× spread. The flat curve was an artifact — this list is what survives scrutiny.
"The flattest curve is also the only one whose 20-iter cells each compile a different program, and whose authors already refuse to prefer small GPU blocks because small blocks would cost kernel launches." — adversarial panel (Grok-4.6)

Release vs main

Each library's tagged release vs latest main, controlled (same account, same hardware).

For amica the release→main diff is 7 commits; only 2cd81e4 ("Make CPU fits faster and much smaller") is perf-relevant and it touches the CPU E-step only — so GPU release≈main (measured identical, full-batch 2.6–2.7 s). On CPU, a single synthetic run does not clearly reproduce a main speedup (auto 3.4 s vs release 2.3 s is within CPU node noise); a paired repeat is needed before claiming a CPU delta. Competitor main builds move only through the same batching knob — pAMICA main is still 12.7 s at 512 on GPU (166 s on CPU). Bumping to main rescues no one's default.
